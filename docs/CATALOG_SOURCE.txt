MASTER DATA AND CLASSIFICATION

The Report implementation must also establish the initial master data for:

- Departments
- Entities
- Projects

These values must be stored in the database as editable master data.

Do not hard-code the lists only inside UI components, filters, validation schemas or reporting queries.

Each master-data record should have, where appropriate:

- stable unique ID,
- display name,
- optional short code,
- sort order,
- active/inactive status,
- createdAt,
- updatedAt.

Use stable IDs in task relations and reporting. Do not use the visible display name as a database identifier.

Existing tasks and reports must continue working if a record is renamed.

Inactive records:
- must remain visible on historical tasks and reports,
- must not be offered for newly created tasks by default,
- must not be deleted if they are already used.

The initial version does not require a complete administration interface for these lists, but the database architecture must allow records to be added, renamed, reordered or deactivated later.

Do not implement Department, Entity or Project as a fixed enum if that would require a code deployment whenever a new value is added.

Projects must remain separate from Requesters.

A Project represents the initiative, campaign or long-running work container.

A Requester represents the person, department or organizational source that requested the task.

Do not use projects as substitutes for requesters.

PROJECT YEAR

Prepare the Project data model for annual project editions.

Add an optional year field to projects.

Examples:

- Najzamestnávateľ 2026
- Ružový október 2026
- Vianočný večierok 2026
- Teambuilding 2026

Do not store the year only as an uncontrolled part of the project name.

Recommended structure:

- baseName
- optional year
- generated or consistently formatted displayName

If the year is empty, display only the base name.

Examples:

- baseName: “Najzamestnávateľ”
- year: 2026
- displayName: “Najzamestnávateľ 2026”

Persistent projects such as “Intranet”, “Klientská zóna” or “Re/Branding” may remain without a year.

Prevent accidental duplicate project editions with the same base project and year.

If “Iné” is selected, provide an optional text field called “Spresnenie projektu”.

TASK RELATIONS

Check the current task schema before adding new fields.

Where equivalent fields already exist:
- reuse or migrate them,
- preserve existing data,
- do not create duplicate parallel fields.

The task should support these separate relations:

- departmentId
- entityId
- projectId
- requesterId or the equivalent existing requester relation

For version 1:

- Department: one primary value
- Entity: zero or one primary value
- Project: zero or one project
- Requester: preserve the existing requester logic

These relations must be available consistently in:

- task creation,
- task editing,
- task detail,
- Report filters,
- Report charts,
- Report task table,
- XLSX export,
- CSV export,
- PDF export,
- image exports,
- API validation.

Filters must load active values from the database rather than from a hard-coded frontend list.

Historical inactive values must remain available when they occur in existing filtered report results.

DATA MIGRATION

Before creating or changing the schema:

1. Inspect existing organization, department, hospital, workplace, project and requester fields.
2. Identify duplicate concepts and naming inconsistencies.
3. Prepare a safe migration or mapping strategy.
4. Preserve all existing task data.
5. Do not silently map uncertain legacy values.
6. Report unmapped values after migration.
7. Make the migration idempotent where practical.

If existing data contains names that appear similar but are not exact matches, do not merge them without an explicit and reviewable mapping.
